## 2026-10-12

### 1. 프로젝트 큰 틀 정리

- **한 줄 요약**: 구버전 LangChain 코드를 최신 버전으로 바꾸고, 바꾼 코드가 실제로 동작하는지까지 확인하는 챗봇
- **문제**: 버전 지체 환각. 인터넷에는 구버전 코드가 더 많아서 LLM이 구버전 방식을 답하고, 틀려도 모른다.
- **차별점**: 문서 근거(RAG) + 실행 근거(import 실행)의 이중 검증
- **파이프라인**: analyzer → retriever → rewriter → verifier → report (verifier 실패 시 retriever로 회귀)
- **증명 방법**: 같은 테스트 코드 30개를 일반 LLM과 우리 시스템에 넣어 import 성공률 비교

### 2. 데이터 출처 조사 → [데이터_출처_조사.md](데이터_출처_조사.md)

- RAG에 넣을 문서와 테스트 코드 출처를 "파일로 한 번에 받을 수 있는 곳" 위주로 조사했다.
- **결정**: RAG 본체는 `llms-full.txt`(최신 공식 문서 전체), 테스트 코드 소재는 GitHub `v0.3` 브랜치 문서
- **발견**: LangChain 전용 변환 쌍(before/after) 데이터셋은 없다. → 테스트셋을 직접 만드는 것 자체가 기여점
- **발견**: python.langchain.com은 docs.langchain.com으로 영구 리다이렉트된다. 구버전 문서는 GitHub에서 받아야 한다.

### 3. 역할 분담 (처음 안, 이후 14번에서 변경)

| 번호 | 역할 | 맡는 것 |
|---|---|---|
| 1번 | 그래프 · 백엔드 | State 정의, LangGraph 연결, API, verifier 구현 |
| 2번 | 데이터 · 검색 | 문서 수집, 벡터DB, retriever |
| 3번 | 변환 · 화면 | analyzer, rewriter, report 프롬프트, Streamlit 화면 |
| 4번 | 검증 · 평가 | 실험 설계, 테스트셋, 비교 실험, 결과 정리 + README, 발표 |

- **4번이 발표와 README까지 맡은 이유**: 4번의 일은 "효과를 숫자로 증명해 설득하는 것"이라 발표와 자연스럽게 이어진다.
- **조정**: 4번의 업무량이 많아지므로 verifier 노드 구현은 1번에게 넘기기로 제안했다.
- **주의**: 검증은 LLM에게 "맞아?"라고 묻는 방식이 아니다. 검증 LLM도 같은 구버전 지식을 가질 수 있기 때문에, 실제 코드 실행 결과로 판정한다. LLM 채점은 쓰더라도 보조 지표로만 쓴다.

### 4. 평가 기준과 실험 규칙 작성 → [eval/EVAL_RULES.md](../eval/EVAL_RULES.md)

- **성공 기준**: 문법 통과 + 모든 import 성공 + 무효 변환 아님
- **공정성**: 같은 모델, temperature 0, 같은 입력 30개, 같은 판정기, baseline 프롬프트 문구 고정
- **지표 8개**: 전체/난이도별 성공률, 1회차/최종 성공률, 검증 루프 효과, 평균 시도 횟수, 경고 비율, classic 의존 비율
- **명시한 한계**: import 성공이 곧 올바른 사용법은 아니다.
- 이후 실험하면서 알게 된 것을 반영해 두 번 고쳤다 (문서 맨 아래 "변경 기록").
  - 테스트셋 형식에 `target_imports`(정답 방향 import) 추가
  - 결과 기록에 `warning_messages`, `uses_community` 추가

### 5. 테스트셋 30개 만들기 → [eval/testset.json](../eval/testset.json)

- 검증 환경을 만들어 설치한 버전: langchain 1.4.4, langchain-core 1.6.9, langchain-openai 1.7.0, langchain-community 0.4.2, langchain-classic 1.0.8, langgraph 1.2.14 (Python 3.12)
- 쉬움/중간/어려움 각 10개. 샘플 12개를 먼저 만들어 확인한 뒤 18개를 더 만들었다.
- **확인 결과**: 30개 모두 최신 환경에서 import가 깨진다. 첫 줄(`ChatOpenAI` 경로)을 빼고 봐도 핵심 줄(체인, 메모리, 에이전트)이 각각 깨진다.
- 항목마다 `target_imports`(정답 방향 import)를 넣고, 최신 환경에서 통과하는 것을 확인했다.
- **발견 1**: `from langchain_classic.chains import LLMChain`은 최신 환경에서 import된다. → classic 우회를 따로 집계해야 한다.
- **발견 2**: `langchain_classic.agents`의 `initialize_agent`, `load_tools`는 의존성 문제로 import에 실패한다. → 어려움 문제는 우회도 잘 안 된다.
- **아직 안 한 것**: 구버전 환경에서 실제로 돌아가는지 확인 (`verified_old: false`)

### 6. 테스트셋 검사기 → [eval/check_testset.py](../eval/check_testset.py)

- old_code가 최신 환경에서 줄마다 깨지는지, target_imports가 통과하는지, 필수 필드, 난이도 값, 중복 id를 검사한다.
- 일부러 잘못 만든 후보(깨지지 않는 코드, 틀린 정답 방향, 난이도 오타, 중복 id)를 모두 걸러내는 것을 확인했다.

### 7. 공용 판정 모듈과 baseline 실험 → [eval/verify.py](../eval/verify.py), [eval/run_baseline.py](../eval/run_baseline.py)

- 판정 로직을 `verify.py`로 분리했다. 일반 LLM(A)과 우리 시스템(B)이 같은 판정기를 써야 공정하기 때문이다.
- 판정 6가지 경우를 시험했다: 구버전 그대로(실패), classic 우회(성공 + 표시), import 삭제(성공 + 무효 의심 표시), 문법 오류(실패), 코드 블록 없는 응답, community 구경로(실패)
- `--mock` 모드(API 호출 없음)로 30개 전체 흐름을 확인했다. 중간에 멈춰도 이어서 실행되도록 항목마다 저장한다.
- **발견 3**: `langchain-community`는 import만 해도 아래 경고를 낸다.
  `DeprecationWarning: langchain-community is being sunset and is no longer actively maintained`
  → 결과에 `uses_community`, `warning_messages`를 기록하도록 추가했다. 발표에서 "버전은 지금도 바뀌고 있다"는 근거로 쓴다.
- **아직 안 한 것**: 실제 OpenAI API로 baseline 실행 (비교 모델 확정 후)

### 8. 결과 그래프 → [eval/make_charts.py](../eval/make_charts.py)

- 그래프 3개(난이도별 성공률, 시도 횟수별 누적 성공률, 성공의 질)와 요약표(`summary.md`)를 만든다.
- 색은 색맹 검증 도구로 구분 가능한지 확인했다. 우리 시스템은 파랑, 일반 LLM은 주황으로 모든 그래프에서 고정했다.
- 가짜 예시 데이터로 그려서 모양만 확인했다. (가짜 데이터와 그림은 저장소에 넣지 않았다.)
- B(우리 시스템) 결과에는 `attempts`, `first_try_success`가 있어야 그래프 2가 그려진다. → verifier를 만드는 3번과 결과 형식을 맞춰야 한다.

### 15. 새 설계와 새 역할에 맞춘 전면 재구성 (2026-10-13)

역할(4번 = 화면 · 평가)과 팀 설계(오프라인 Qdrant · symbol_map, verifier (a)(b), 재시도 2~3회)가 바뀌어서, 지금까지 만든 자료를 새 기준으로 다시 만들었다. 예전 자료는 지우지 않고 "이전 버전"으로 남겼다.

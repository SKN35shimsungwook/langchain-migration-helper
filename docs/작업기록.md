## 지금 기준 (2026-10-13)

**역할**

| 번호 | 역할 | 맡는 것 |
|---|---|---|
| 1번 | 그래프 · 백엔드 | State, 단계 연결, 다시 갈지 판단, API, 샌드박스 환경 |
| 2번 | 데이터 · 검색 | 가이드 · 릴리스 노트 → Qdrant, `symbol_map.json`, retriever |
| 3번 | 변환 · 검증 | analyzer, rewriter, verifier (a) 근거 ID 확인 (b) import · 속성 검증, report |
| **4번** | **화면 · 평가** | Streamlit 화면, 평가 설계 · 실험 + 보고서 · README · 발표 |

**팀 사이 약속 (합의안 3종)**

```text
2번 symbol_map · Qdrant ──같은 근거 ID──▶ 3번 report ──▶ 1번 run_migration() ──┬──▶ 4번 화면
   (symbol_map 합의안)                    (출력 모양 합의안)  (API 합의안 1.1)      └──▶ 4번 평가
```

**주요 결정**

| 결정 | 이유 |
|---|---|
| 검증은 LLM에게 묻지 않고 **실제 실행**으로 판정 | 검증하는 LLM도 같은 구버전 지식을 가질 수 있음 |
| 평가 판정기 `verify.py`를 3번 verifier (b)의 출발점으로 넘김 | 파이프라인 검증과 평가 채점이 같은 기준이어야 공정함 |
| 3번과는 **report 모양 하나만** 합의, 평가 결과는 4번이 report에서 계산 | 3번이 평가용 파일을 따로 만들 필요가 없음 |
| 검증 실패도 HTTP 200, HTTP 에러는 서버 문제일 때만 | 평가에서 "변환 실패"와 "서버 고장"을 구분 |
| 근거 ID는 `문서#섹션-번호`, symbol_map · Qdrant · report에서 같은 문자열 | verifier (a), 화면 링크, 근거 일치율이 한 ID로 연결됨 |
| classic 우회와 community 사용은 성공으로 인정하되 **따로 집계** | 통과했지만 최신 방식이 아니거나 곧 깨질 코드를 구분 |
| 이전 자료는 지우지 않고 "이전 버전" 표시 | 사용자 요청 |
| 화면이 팀 그래프를 **함수로 바로 부르는 것**을 기본안, HTTP는 선택 | 팀 저장소에 FastAPI가 없고 화면(`app.py`)이 같은 저장소에 있음 → 1번이 만들 것이 함수 하나로 줄어듦 |
| 목표 버전 `target_version` 추가 (지금은 `1.x`) | 팀 대화에서 "버전을 골라서 돌리는 챗봇"으로 정함 |
| symbol_map 파일 모양은 그대로, `MigrateState`와 **연결표**만 추가 | 1번이 만든 이름을 존중하고, 2번이 다시 만들 일을 줄임 |
| 공개 문서에는 팀원 이름 · 대화 원문을 넣지 않고 **역할 번호**로만 | 공개 저장소라서 (사용자 요청) |
| 팀 저장소는 이 작업에서 **건드리지 않음** (4번 브랜치 포함). 올리는 일은 4번이 직접 | 사용자 요청 |

**정정 기록**

| 날짜 | 처음 기록 | 바로잡은 내용 |
|---|---|---|
| 2026-10-13 | `langchain_classic.agents`의 `initialize_agent`, `load_tools`는 import 실패 → 어려운 문제는 우회가 잘 안 됨 | `initialize_agent`, `AgentType`, `AgentExecutor`는 classic 우회로 **됨**. 안 되는 것은 `load_tools`뿐. 처음에 여러 이름을 한 줄로 가져와 전부 실패처럼 보였음 → classic 의존 비율을 따로 보는 것이 더 중요해짐 |

## 날짜별 기록

### 2026-10-12 · 기획과 평가 준비

**1. 프로젝트 큰 틀** — 구버전 LangChain 코드를 최신 버전으로 바꾸고 실제로 동작하는지까지 확인하는 챗봇. 문제는 버전 지체 환각(인터넷에 구버전 코드가 많아 LLM이 틀려도 모름), 차별점은 문서 근거 + 실행 근거의 이중 검증, 증명은 같은 30문제로 일반 LLM과 비교.

**2. 데이터 출처 조사** → [데이터_출처_조사.md](데이터_출처_조사.md)
- RAG 본체는 `llms-full.txt`, 테스트 코드 소재는 GitHub `v0.3` 브랜치 문서로 결정.
- LangChain 전용 변환 쌍 데이터셋은 없음 → 테스트셋을 직접 만드는 것 자체가 기여점.
- python.langchain.com은 docs.langchain.com으로 영구 리다이렉트 → 구버전 문서는 GitHub에서.

**3. 처음 역할 분담** (이후 2026-10-13에 변경)
- 1 그래프·백엔드 / 2 데이터·검색 / 3 변환·화면 / 4 검증·평가 + README · 발표. verifier 구현은 1번에게 넘기자고 제안했었음.

**4. 평가 규칙** → [EVAL_RULES.md](../eval/EVAL_RULES.md)
- 성공 기준, 공정 조건(같은 모델, temperature 0, 같은 입력, 같은 판정기, baseline 문구 고정), 지표를 먼저 정함.

**5. 테스트셋 30개** → [testset.json](../eval/testset.json)
- 검증 환경: langchain 1.4.4, langchain-core 1.6.9, langchain-openai 1.7.0, langchain-community 0.4.2, langchain-classic 1.0.8, langgraph 1.2.14 (Python 3.12).
- 쉬움 · 중간 · 어려움 각 10개. 30개 모두 최신 환경에서 깨지고, 첫 줄을 빼도 핵심 줄(체인, 메모리, 에이전트)이 각각 깨짐. 정답 방향 `target_imports`는 모두 통과.
- 발견: `langchain_classic`으로 우회하면 `LLMChain`도 import됨 → classic 우회를 따로 집계. (에이전트 쪽 우회 기록은 위 정정 기록 참고)
- 아직 안 한 것: 구버전 환경에서 실제로 돌아가는지 확인.

**6. 테스트셋 검사기** → [check_testset.py](../eval/check_testset.py) — 일부러 틀린 후보(안 깨지는 코드, 틀린 정답 방향, 난이도 오타, 중복 id)를 모두 걸러냄.

**7. 판정기와 baseline 실험** → [verify.py](../eval/verify.py), [run_baseline.py](../eval/run_baseline.py)
- 판정 로직을 분리해서 A와 B가 같은 판정기를 쓰게 함. `--mock`으로 30개 흐름 확인.
- 발견: `langchain-community`는 import만 해도 "지원 종료 중" 경고 → `uses_community`, `warning_messages` 기록. 발표에서 "버전은 지금도 바뀌고 있다"는 근거.

**8. 결과 그래프** → [make_charts.py](../eval/make_charts.py) — 그래프 3장(난이도별, 시도 횟수별 누적, 성공의 질)과 요약표. 색맹 검증한 색, 시스템별 색 고정. 가짜 데이터로만 확인(저장소에 넣지 않음).

**9. 발표 자료 · README** — 13장 초안(발표자 노트 포함, 결과 자리는 `[__]`), README를 같은 흐름으로 작성. 슬라이드 원본을 저장소에 복사하고 웹 · PDF 변환 스크립트를 둠.

**10. 쉬운 안내서 v1** → [guide/](guide/) (지금은 이전 버전)
- 처음 쓴 역순설계 문서가 어렵다는 피드백 → **주방 비유**로 다시 씀 (import = 서랍에서 도구 꺼내기, 4번 = 요리 대회 심사위원).

**11. GitHub 공개** — 커밋은 작업 단위별, 한국어 `<타입>: 무엇을`. 올리기 전에 비밀 정보 검사, 가상환경과 `.env`는 `.gitignore`. 공개 저장소라 개인 정보는 기록하지 않음(발표자 노트도 공개됨).

**12. 그림 자료** → [images/](images/)
- 글이 많다는 피드백 → 설명을 움직이는 SVG로 바꿈. 정지 화면(PDF)에서도 내용이 보이도록 "완성 → 잠깐 비움 → 다시 채움" 순서로 움직이게 함.

- 팀 대화 정리(역할 번호로): 서비스는 "버전을 골라 돌리면 새 코드와 검증 리포트가 나오는 챗봇", 역할 1~4 확정, 각자 브랜치 → dev PR, 매일 13:40 모임, 데이터는 원문과 벡터 DB를 Git에 올리기로 함, 동작하는 최소 버전 먼저.
- 미정: report 노드 담당(3번 또는 4번), 병합 담당, 비교 모델.
- 그림 3장 추가: 11 팀 진행 상황판, 12 두 가지 report, 13 팀 Git 흐름.

**20. 팀 코드에 맞춰 화면 · 합의안을 1.1로**
- 화면: 목표 버전 선택, "목표 LangChain 1.x" 배지. 부르는 방법 세 가지(함수 `MIGRATION_FUNC` → HTTP `MIGRATION_API_URL` → 가짜 응답).
- 합의안: API 0장(함수 호출 기본안), report에 `target_version`, symbol_map 0장(`MigrateState` 연결표), report 노드 담당 확인 중 표시.
- 확인: 예시 report 2개 형식 검사 + `verify.py` 판정 일치, 가짜 응답 30개 형식 문제 0개, 가짜 그래프 함수로 화면 · 평가 연결(그래프 오류 · 함수 못 찾음 안내 확인), 연습용 서버가 지원하지 않는 버전에 400 응답, 화면 자동 테스트에서 버전 선택 · 배지 확인.

**21. 오늘 물어본 것**
- report 노드 ≠ 결과 보고서 (영수증 vs 대회 결과 보고서). 보고서는 4번 확정.
- 4번 브랜치가 main 상태에 멈춰 있어 dev 최신으로 앞당김(사용자 요청, 잃은 작업 0개). **이후 팀 저장소는 건드리지 않기로 함.**
- PowerShell 5.1에서 `&&` 에러 → 한 줄씩 실행. 다른 Git 폴더(`eq-test`) 안에 내려받은 팀 저장소는 바탕화면으로 옮기기.

**22. 팀 저장소용 사본 폴더** → [for_team_repo/](../for_team_repo/)
- 팀 저장소와 같은 구조로 4번 파일만 모음: `app.py`(화면), `src/ui/backend.py`, `eval/`, `docs/`(합의안 · 예시). 원본은 그대로 하나만 두고 [tools/make_team_copy.py](../tools/make_team_copy.py)가 사본을 만듦 (경로와 import만 팀 구조에 맞게 바꿈).
- 확인: 팀 dev를 임시 폴더에 꺼내 사본을 덮어씀 → 바뀌는 기존 파일은 `app.py` 하나, 나머지는 새 폴더. 화면(가짜 응답 · 팀 그래프 함수 연결), 형식 검사, 시험지 30/30, 우리 시스템 실험기 모두 정상. 팀 저장소 자체는 건드리지 않음.

**23. 팀 보고 준비** → [04 팀 보고 준비](guide_v2/04_팀_보고_준비.md) (MD · HTML · PDF)
- "평가 도구랑 화면 뼈대는 거의 만들어 뒀어요"를 풀어 씀: 4번이 만든 것을 **팀이 바로 쓸 수 있는 순서**(3번 채점 로봇 → report 검사기 → 1번 함수 모양 → 2번 검사기 → 화면 → 시험지 → 일반 AI 시험 기계)로, "거의"의 범위(도구 완성, 결과 숫자는 챗봇 필요)를 정직하게.
- 팀 저장소에서 새로 만든다고 가정한 순서: 남을 기다리지 않는 일 먼저. **일반 AI(A) 실험은 팀 챗봇 없이 API 키만 있으면 지금 가능.**
- 보고 방법: 말하는 원칙 3가지, 회의 1분 대본, 디스코드 공지, 역할별 1:1 메시지, PR 설명, 예상 반응과 답. 그림 14(4번이 팀에 건네는 것) 추가.

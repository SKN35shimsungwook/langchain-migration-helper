# report 출력 모양 합의안 (3번 ↔ 4번)

> 버전 1.1 · 2026-10-13 · 작성: 4번 (화면 · 평가) · 받는 사람: 3번 (변환 · 검증)
> 상태: **합의 전 (초안)** — 아래 "정할 것"에 답해 주면 확정합니다.
> 1.1 변경: `target_version`(목표 버전) 필드 추가. 팀 저장소에는 HTTP API 대신 **함수 호출**(`run_migration(code, target_version) → report`)이 기본안입니다 ([API_합의안.md](API_합의안.md) 0장). report 모양은 그대로입니다.
> **report 노드 담당은 아직 확정 전**입니다. 화면에 보여 줄 모양을 4번이 정했으므로 4번이 맡을 수도 있습니다 (회의에서 확인).

## 한 줄 요약

**3번은 report를 아래 모양 하나로만 돌려주면 됩니다.**
화면은 이걸 그대로 보여 주고, 평가 결과(성공률, 1회차 성공, 근거 일치율)는 4번이 이 report에서 직접 계산합니다. 평가용 파일을 따로 만들 필요가 없습니다.

```text
3번 파이프라인 ──report(JSON)──▶ 1번 API ──┬──▶ 화면 (4번): 그대로 보여 주기
                                          └──▶ 평가 (4번): run_system.py가 30문제 결과로 변환
```

## 1. 모양

```json
{
  "contract_version": "1.1",
  "target_version": "1.x",
  "original_code": "입력된 구버전 코드",
  "migrated_code": "최종 변환 코드",
  "changes": [
    {
      "old": "구 코드 한 줄",
      "new": "새 코드 한 줄",
      "reason": "바꾼 이유",
      "evidence_id": "근거 ID (2번 Qdrant / symbol_map 의 ID)",
      "evidence_url": "근거 문서 링크 또는 null",
      "evidence_ok": true
    }
  ],
  "verification": {
    "success": true,
    "fail_stage": null,
    "error": null,
    "checked_attributes": ["PromptTemplate.from_template"]
  },
  "attempts": 2,
  "attempt_log": [
    {"attempt": 1, "fail_stage": "import", "error_type": "ModuleNotFoundError", "target": "langchain.chains", "message": "No module named 'langchain.chains'"},
    {"attempt": 2, "fail_stage": null, "error_type": null, "target": null, "message": null}
  ]
}
```

전체 예시: [성공 예시](contracts/report.example.json) (2회 만에 통과) · [실패 예시](contracts/report_fail.example.json) (3회 모두 실패)

## 2. 필드 설명

| 필드 | 형식 | 채우는 단계 | 화면에서 | 평가에서 |
|---|---|---|---|---|
| `contract_version` | 문자열 `"1.1"` | report | – | 모양이 바뀌었는지 확인 |
| `target_version` | 문자열 `"1.x"` | 입력 그대로 | "목표 LangChain 1.x" 배지 | 어느 버전 기준 결과인지 기록 |
| `original_code` | 문자열 | 입력 그대로 | 변경 전 코드 | – |
| `migrated_code` | 문자열 | rewriter (마지막 시도) | 변경 후 코드, 바뀐 줄 | **verify.py로 다시 판정** |
| `changes[]` | 목록 | rewriter | 변경표 | 근거 일치율 |
| `changes[].old` / `new` | 문자열 | rewriter | 구 → 신 | – |
| `changes[].reason` | 문자열 | rewriter | 이유 | – |
| `changes[].evidence_id` | 문자열 | rewriter | – | – |
| `changes[].evidence_url` | 문자열 또는 null | retriever 결과에서 | "문서 열기" 링크 | – |
| `changes[].evidence_ok` | true / false | **verifier (a)** | 근거 확인 배지 | **근거 일치율** = true 개수 ÷ 전체 |
| `verification.success` | true / false | **verifier (마지막 시도)** | 검증 배지 | 파이프라인 판정과 평가 판정이 같은지 확인 |
| `verification.fail_stage` | 아래 표의 값 또는 null | verifier | 실패 이유 | 실패 원인 분포 |
| `verification.error` | 문자열 또는 null | verifier | 실패 메시지 | – |
| `verification.checked_attributes` | 문자열 목록 | verifier (b) | – | 기록용 |
| `attempts` | 정수 | 1번 그래프의 시도 횟수 | "2회 시도" | 평균 시도 횟수 |
| `attempt_log[]` | 목록 (시도 수만큼) | verifier가 시도마다 한 줄 | 진행 기록 | **1회차 성공** = 첫 줄의 `fail_stage`가 null |

### `fail_stage` 값

| 값 | 뜻 | 누가 판정 |
|---|---|---|
| `null` | 통과 | – |
| `"syntax"` | 문법 오류 | verifier (b) |
| `"import"` | import 실패 (경로 틀림, 없는 모듈) | verifier (b) |
| `"attribute"` | import 한 이름의 속성이 없음 (없는 기능 지어냄) | verifier (b) |
| `"evidence"` | 근거 ID가 실제 검색 결과에 없음 | verifier (a) |
| `"timeout"` | 검증 시간 초과 | verifier (b) |

## 3. 지켜 줄 규칙 5가지

1. **필드 이름과 형식은 바꾸지 않습니다.** 필드를 더 넣는 것은 괜찮습니다. 빼거나 이름을 바꿔야 하면 `contract_version`을 올리고 4번에게 알려 주세요.
2. **값이 없으면 빈칸 대신 `null`**을 넣습니다. (예: 통과한 시도의 `error_type`)
3. **`attempt_log` 줄 수 = `attempts`**, `attempt`는 1부터 차례대로.
4. **성공이면** `verification.success`가 true, `fail_stage`가 null이고, 마지막 시도 줄도 통과여야 합니다.
5. **verifier (b)는 `eval/verify.py`의 `judge()`를 출발점으로** 써 주세요. 4번 평가도 같은 함수로 다시 판정하므로, 기준이 같아야 결과가 일치합니다.

```python
# verifier (b) 예시 — eval/verify.py 를 그대로 쓰는 경우
from verify import judge
r = judge(migrated_code, py=샌드박스_python_경로)
# r["success"], r["fail_stage"] ("syntax" / "import" / "attribute" / "timeout"), r["error"], r["checked_attributes"]
```

## 4. 맞는지 확인하는 방법

4번이 만든 검사기로 report 파일을 바로 확인할 수 있습니다.

```bash
cd eval
python check_contract.py my_report.json
python check_contract.py my_report.json --py verify-env/Scripts/python.exe   # verify.py 판정과 같은지까지
```

`[PASS]`가 나오면 화면과 평가에 바로 연결됩니다. `[FAIL]`이면 무엇이 다른지 한 줄씩 알려 줍니다.

## 5. 정할 것 (3번 답변 필요)

| # | 질문 | 4번 제안 |
|---|---|---|
| 1 | 최대 시도 횟수는 2회인가요, 3회인가요? | 3회 (평가 규칙 기본값) |
| 2 | `evidence_id` 모양은? (2번과 함께) | `문서#섹션-번호`, 예: `v1-migration#llmchain-03` ([symbol_map 합의안](symbol_map_합의안.md) 2장에서 2번에게 제안) |
| 3 | `evidence_url`은 retriever 결과에서 채울 수 있나요? | 가능하면 채우고, 없으면 null |
| 4 | 변경이 import가 아닌 줄(예: `LLMChain(...)` → `prompt \| llm`)도 `changes`에 넣나요? | 넣기 (화면 변경표와 근거 일치율에 필요) |
| 5 | verifier (a)에서 실패하면 `fail_stage`를 `"evidence"`로 적고 재시도하나요? | 예 |
